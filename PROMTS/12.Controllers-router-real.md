## 3. Contexto del proyecto

El proyecto utiliza PHP nativo 8.1+, MySQL/MariaDB mediante PDO, HTML, CSS y JavaScript nativo, y se ejecuta localmente mediante XAMPP.

Actualmente:

- `backend/routes/web.php` funciona como un mapa de referencia de las rutas, pero todavía no cuenta con un router real.
- Los archivos de `admin/` y `cliente_interfaces/` funcionan como shims que realizan `require` directo de las vistas.
- La aplicación ya tiene URLs públicas que deben continuar funcionando.
- Existen controladores dentro de `backend/controllers/`, cuya estructura y responsabilidades deben revisarse antes de implementar cambios.

No supongas que una ruta, controlador, vista o método existe sin verificarlo en el proyecto.

## 4. Objetivo

Implementar un router mínimo y funcional que utilice `backend/routes/web.php` como definición real de las rutas de la aplicación.

El router debe permitir que las solicitudes sean dirigidas al controlador y método correspondientes.

Los controllers deben encargarse de recibir la solicitud, ejecutar las validaciones necesarias y renderizar la vista correspondiente, conservando el comportamiento y las URLs públicas actuales.

La implementación debe mantener la compatibilidad con las funcionalidades existentes y evitar duplicar lógica entre los shims, el router y los controllers.

## 7. Implementación del router

### 7.1. Crear `backend/Router.php`

Implementa un router mínimo en PHP nativo, sin dependencias externas.

Debe permitir:

- Registrar rutas.
- Asociar una URL con un método HTTP.
- Asociar una ruta con un controller y una acción.
- Resolver la solicitud actual.
- Ejecutar la acción correspondiente.
- Manejar rutas inexistentes mediante una respuesta HTTP 404.
- Manejar métodos HTTP no permitidos mediante una respuesta HTTP 405, cuando corresponda.
- Evitar que una ruta no registrada ejecute una vista de manera accidental.

La implementación debe seguir las convenciones existentes del proyecto.

No introduzcas un sistema de enrutamiento complejo ni funcionalidades que no sean necesarias para este alcance.

### 7.2. Utilizar `backend/routes/web.php`

Convierte `backend/routes/web.php` en el archivo que registra las rutas reales de la aplicación.

Debe utilizar el router implementado en `backend/Router.php`.

El archivo debe dejar de ser únicamente un mapa de referencia.

Mantén una definición clara y centralizada de las rutas públicas existentes.

Evita duplicar la definición de las mismas rutas en varios archivos.

### 7.3. Controllers

Revisa los controllers existentes en `backend/controllers/`.

Implementa o adapta los controllers necesarios para que:

- Reciban la solicitud correspondiente.
- Ejecuten las validaciones necesarias.
- Utilicen los servicios existentes cuando corresponda.
- Rendericen las vistas adecuadas.
- Mantengan los permisos y controles de acceso actuales.
- Conserven los mensajes y comportamientos existentes.
- Eviten duplicar lógica de negocio que ya se encuentre en servicios.

No conviertas los controllers en archivos que contengan toda la lógica del sistema.

No dupliques las funciones de autenticación, productos, inventario, carrito, cupones o pedidos que ya fueron abordadas en prompts anteriores.

Reutiliza las implementaciones existentes cuando sean aplicables.

### 7.4. Shims de `admin/` y `cliente_interfaces/`

Convierte los shims existentes para que invoquen el router o el controller correspondiente.

Los shims deben conservar las URLs públicas actuales.

No deben contener lógica de negocio ni duplicar la lógica de los controllers.

Evita que los shims realicen `require` directo de las vistas cuando la solicitud deba pasar por el router.

Antes de realizar cada modificación, verifica cómo se accede actualmente a la vista y qué comportamiento debe conservarse.

### 7.5. Compatibilidad de URLs

Todas las URLs públicas existentes deben continuar funcionando.

Conserva:

- Las rutas actuales.
- Los parámetros que utilicen las vistas.
- Los métodos HTTP requeridos.
- Los controles de autenticación y autorización.
- Las redirecciones existentes.
- Los mensajes y comportamientos funcionales.
- Los recursos estáticos y enlaces que dependan de las rutas actuales.

No cambies las URLs públicas para adaptarlas al nuevo router.

### 7.6. Archivo `.htaccess`

Modifica `.htaccess` únicamente si es necesario para que el router funcione correctamente.

Antes de realizar cualquier cambio:

- Inspecciona las reglas existentes.
- Identifica las reglas que afectan las URLs públicas.
- Conserva las reglas necesarias para los recursos estáticos.
- Evita redirigir recursos existentes de forma incorrecta.
- No introduzcas reglas que generen ciclos de redirección.
- No alteres configuraciones que no estén relacionadas con el enrutamiento.

Si el router puede funcionar sin modificar `.htaccess`, no lo modifiques.
